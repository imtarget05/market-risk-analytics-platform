# ADR-0002: Deployment, Security & Rollback Strategy

## Context

The Market Risk Analytics Platform calculates VaR, Expected Shortfall, Monte Carlo simulation,
and stress-testing results for financial portfolios. As we move from local development to
production deployment, we document decisions around container security, authentication,
rate limiting, database migration, and rollback.

## Decision

### Container Security

- **Base image**: `python:3.11-slim` pinned by digest
- **Multi-stage build**: Builder stage for dependencies, runtime stage for app only
- **Non-root user**: Container runs as `app` user (uid 1000)
- **No secrets in image**: `.dockerignore` excludes `.env`, `*.db`, `test_*.db`
- **Image tagging**: Git commit SHA + immutable digest; no `latest` tag in production

### Authentication & Authorization

- **Auth mechanism**: JWT (HS256) with 30-minute expiry
- **Token endpoint**: `POST /api/v1/auth/login` (account_number → bearer token)
- **Registration**: `POST /api/v1/auth/register` (admin only)
- **RBAC roles**: `viewer` (read-only), `analyst` (portfolios, positions, prices, risk calc), `admin` (user management)
- **Role hierarchy**: viewer < analyst < admin
- **Protected endpoints**: Portfolio creation, position creation, price ingestion, risk calculation, stress testing require `analyst` role

### Rate Limiting

- **Mechanism**: In-memory sliding window (Redis-backed in production)
- **Default limit**: 100 requests per 60 seconds per client IP
- **Fail-closed**: Excess requests return HTTP 429
- **Test bypass**: `TESTING=true` environment variable disables rate limiting

### Database Migrations

- **Tool**: Alembic
- **Migration files**: Versioned under `src/backend/alembic/versions/`
- **Startup behavior**: No auto `create_all`; migrations run explicitly via `alembic upgrade head`
- **Production deployment**: Migration runs as init container or pre-deploy step before app starts
- **Rollback**: `alembic downgrade <version>` for backward-compatible changes only

### Rollback Strategy

- **Image rollback**: Revert to previous image digest in K8s Deployment
- **Database rollback**: `alembic downgrade` for backward-compatible schema changes; data rollback via backup restore
- **Rollback drill**: Required before production release

### Failure Scenarios

| Scenario | Mitigation |
|----------|-----------|
| Invalid JWT token | Return 401 Unauthorized |
| Insufficient role | Return 403 Forbidden |
| Rate limit exceeded | Return 429 Too Many Requests |
| DB connection failure | Return 503; circuit breaker planned for P2 |
| Empty price history | VaR/ES return 0; Monte Carlo returns 0 |
| Migration failure | Deploy blocks; rollback to previous image + `alembic downgrade` |

## Alternatives Considered

- **OAuth2 / OpenID Connect**: Rejected for MVP; JWT with account_number is simpler
- **API keys**: Rejected; JWT provides better expiry semantics
- **Session-based auth**: Rejected; stateless JWT is better for horizontal scaling

## Consequences

### Positive

- Strong auth/RBAC model suitable for risk analytics platform
- Container follows security best practices (non-root, digest-pinned)
- Versioned database migrations enable safe schema evolution
- Clear rollback procedure documented

### Negative

- JWT secrets must be rotated periodically; no automatic rotation in MVP
- In-memory rate limiting doesn't survive pod restarts; Redis-backed required for production
- No refresh token rotation in MVP (planned for P2)
